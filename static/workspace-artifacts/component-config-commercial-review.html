Review started from frog task component-config-commercial-review.

The aim is to turn the workspace's components into sellable configurations that customers can buy, enable, compose, and let discover/interact with each other without custom one-off wiring.

Method

  • Used frog for task state and locks.

Configuration Surfaces Observed

The workspace already has many configuration surfaces, but they are not yet a single product configuration system:

  • Environment files: .env, .env.example, .env.compose.example, service secrets, Stripe, Cloudflare, DNS, Infisical, Wordfence, SMTP.
  • Runtime manifests: docker-compose.yml, systemd units, reverse proxy snippets, Wrangler configs, Docusaurus configs, Cargo and Python package manifests.
  • API surfaces: GraphQL, REST, webhooks, MCP, SSE, WebSocket, SMTP, IMAP, Cloudflare Workers, Prometheus metrics.
  • Operator surfaces: frog, rp, mailstack_ops.py, Rust CLIs/TUIs, Make targets, setup scripts.
  • Documentation surfaces: README files, Docusaurus docs, offer deploy bundles, product atlas pages.

The missing layer is a normalized component manifest that states what each component is, what it can do, what it needs, what it exposes, and how another component may safely use it.

Existing Interaction Patterns

The following patterns already recur enough to standardize:

  • WordPress content is exposed to storefronts through GraphQL.
  • Gatekeeper protects WordPress ingress and exposes health, metrics, upload, webhook, and management APIs.
  • Provisioning creates tenants and wires DNS, secrets, mail, billing, and Docker Compose stacks.
  • Mail components expose GraphQL/REST/MCP and relay via SMTP/Cloudflare Worker.
  • Payment events arrive through Stripe webhooks and update tenant/package state.
  • Artifacts move through Docker registry, OCI/ORAS-like flows, and static site deploy bundles.
  • Agents coordinate through frog tasks, locks, event logs, and MCP.

These are enough to define a practical first version of component discovery: identity, capabilities, endpoints, events, secrets, dependencies, health, and commercial metadata.

Immediate Gaps

  1. No shared component manifest.
  2. No capability taxonomy for matching components.
  3. No runtime registry that services can query for peers.
  4. No common consent or authorization model for cross-component calls.
  5. No package-level view that turns components into clear SKUs.
  6. No standard config UX for picking packages, supplying secrets, accepting dependencies, and previewing cost/support impact.
  7. No compatibility test suite proving that discovered components can actually interact.
  8. Docs and offer pages are not yet generated from a package/component model.

The workspace already contains enough mature pieces to sell configurations, but the configuration model is implicit and repo-local. The next review slices should convert this inventory into:

  2. package/SKU definitions,
  3. a component manifest and capability taxonomy,
  4. a registry and interaction contract,
  5. a consent/security boundary,

The strongest near-term sales stories are not generic "platform" claims. They are narrow outcomes:

  • Keep WordPress editorial workflow while adding commerce and a hardened edge.
  • Run a secure managed WordPress runtime with observable ingress and backups.
  • Operate Proton/IMAP mail with rules, reputation, encryption, and audit.
  • Compose publishing/media workflows from reusable pipeline components.

The weaker stories are the ones that currently require the buyer to understand too much internal plumbing: registry, Infisical, Mailstack, and frog should be sold as included managed capabilities unless a specific technical buyer asks for them directly.

Component Discovery Manifest

Each component should publish a small manifest at a stable path such as ragbaz.component.json or component.ragbaz.yaml. The manifest should be checked into the component repo and optionally exported into a runtime registry.

Minimum fields:

name: Secure WordPress Gatekeeper
version: 0.1.0
kind: service
owner: ragbaz
repo: products/articulate/gatekeeper
commercial:
  package_tags: [secure-wordpress-runtime]
  audience_tags: [site-owner, agency, publisher]
  support_tier: managed
capabilities:
  - wordpress.ingress
  - wordpress.uploads.hardened
  - wordpress.graphql.guardrails
requires:
  secrets:
    - GATEKEEPER_SHARED_SECRET
    - RAGBAZ_AUTH_MANAGEMENT_SECRET
  services:
    - wordpress.origin
    - reverse_proxy.http
provides:
  endpoints:
    - name: health
      url_env: GATEKEEPER_HEALTH_URL
      protocol: http
    - name: upload
      url_env: GATEKEEPER_UPLOAD_URL
      protocol: http
  events:
    - content.changed
    - upload.accepted
health:
  checks:
    - type: http
      target: /healthz
docs:
  readme: products/articulate/gatekeeper/README.md
  public: https://doc.ragbaz.cc/docs/products/articulate/gatekeeper

Recommended manifest sections:

  • identity: stable id, name, version, repo path, owner, lifecycle status.
  • commercial: package tags, personas, support tier, sales status, pricing tags, demo URL.
  • capabilities: normalized capability ids and human labels.
  • requires: secrets, services, DNS records, storage, network, billing, and human approvals.
  • provides: endpoints, events, artifacts, CLIs, MCP tools, queues, metrics, docs, and admin surfaces.
  • config: required knobs, optional knobs, defaults, validation rules, and whether each knob is tenant/customer/operator controlled.
  • security: auth method, token scopes, tenant boundary, data classes, secret access, revocation path.
  • health: liveness, readiness, dependency checks, synthetic smoke tests.
  • compatibility: contract test names, supported versions, known incompatible components.

Manifest rule: every sellable package should be expressible as a set of component manifests plus package-level defaults, not as a bespoke README recipe.

Runtime Registry Review

The registry should have two layers:

  1. Source registry: manifests checked into repos and discoverable by frog.
  2. Runtime registry: active deployments publish resolved endpoint, health, version, and tenant-specific config state.

Options reviewed:

DNS/SRV recordsGood for deployed service lookupWeak for capabilities, secrets, pricingOptional runtime endpoint hint

Recommended MVP:

  1. Add manifest files to the first five package-critical components: Gatekeeper, ragbaz-provision, Articulate storefront, MailGuard, Mailstack.
  2. Teach frog to scan and validate manifests into AGENTS.db as source metadata.
  3. Add a provisioner-side runtime table for tenant component instances: component id, version, tenant, health URL, public URL, internal URL, granted capabilities, and status.
  4. Expose read-only registry queries through GraphQL/REST/MCP before allowing components to mutate registry state.
  5. Later, generate docs/offer pages from package manifests and registry status.

Runtime lookup rule: components should ask for a capability plus tenant context, not for a hard-coded service name. Example: "find provider of mail.relay for tenant xtas" should resolve to Mailstack or MailGuard depending on grants and package configuration.

Inter-Component Interaction Contracts

Components should interact through a small number of contract shapes:

Contract shapeUse whenRequired fieldsCurrent examples

Artifact handoffComponent produces material outputartifact id, media type, digest, storage URL, provenance, signatureregistry, ORAS/cosign, docs static builds

Cross-component contract rules:

  • Every mutation must be idempotent or explicitly marked non-idempotent.
  • Every request carries tenant/package context, even if the component is currently single-tenant.
  • Every event has a schema version and stable event id.
  • Every webhook has a signature and replay protection.
  • Every artifact has a digest and producer identity.
  • Every component publishes a health contract separate from business APIs.
  • Every failure response uses a shared shape: code, message, retryable, component id, correlation id.
  • Every component interaction should be auditable by tenant, package, and capability.

First contract standard to implement:

{
  "correlation_id": "uuid",
  "tenant": "xtas",
  "package": "secure-wordpress-runtime",
  "capability": "wordpress.ingress",
  "source_component": "articulate.provision",
  "target_component": "articulate.gatekeeper",
  "idempotency_key": "optional-for-mutations"
}

This envelope can be carried in HTTP headers, GraphQL extensions, event payloads, or MCP tool metadata.

Auth, Consent, And Tenant Boundaries

"At will" interaction should mean "after discovery, permission, and audit," not unrestricted cross-component calls.

Required model:

  • Service identity: every component instance has an identity separate from human users and tenants.
  • Tenant grant: a tenant or operator grants one component permission to use another component's capability.
  • Capability scope: grants are capability-scoped, for example mail.relay:send or wordpress.media:write.
  • Package default: packages can propose default grants, but activation must record who accepted them and when.
  • Secret isolation: components request secret references, not raw secrets, unless the grant explicitly permits materialization.
  • Revocation: every grant has a revocation path and components must handle revoked peers as normal runtime failure.
  • Audit: every cross-component call records source, target, tenant, capability, grant id, correlation id, and result.

Grant shape:

{
  "grant_id": "uuid",
  "tenant": "xtas",
  "package": "secure-wordpress-runtime",
  "source_component": "articulate.storefront",
  "target_component": "articulate.gatekeeper",
  "capabilities": ["wordpress.graphql:read", "wordpress.media:read"],
  "expires_at": null,
  "created_by": "operator-or-tenant-user",
  "created_at": "timestamp",
  "revoked_at": null
}

Boundary rules:

  • Cross-tenant calls are denied by default.
  • Package-level automation may operate only inside the package tenant boundary.
  • Human-controlled external actions, such as community posting or DNS changes, require explicit approval.* capabilities.
  • Billing-affecting calls require a visible package/tenant cost context.
  • Components that handle hostile samples, mail, payments, secrets, or auth must be marked as sensitive in the manifest.

First implementation target: add grant metadata to the proposed runtime registry before allowing automatic component-to-component mutation calls.

Configuration UX Review

The first UI does not need to be a large product. It can be an operator-facing configuration wizard generated from package and component manifests.

Required screens:

  1. Package selection: choose Secure WP Starter, Course and Shop, MailGuard, etc.; show outcome, included capabilities, price axis, and support tier.
  2. Tenant/site identity: slug, domain, owner email, region, support contact.
  3. Dependency check: required services, DNS, secrets backend, registry, storage, Stripe/Cloudflare availability.
  4. Secrets and grants: collect or reference secrets; show which component will receive which capability grant.
  5. Configuration knobs: defaults first, advanced controls hidden; every knob says whether customer, operator, or system owns it.
